# A/B 結果（追加実験 D）: 受け入れテストを前提にした「Codex 実装 + Claude 軽量レビュー」と Opus 単独

実行: 2026-10-04。設計と判定基準: [sandwich-ab-d-design.md](sandwich-ab-d-design.md)（凍結コミット `e614c29`、本番の run を 1 つも始める前に凍結）。前回の実験: [sandwich-ab-results.md](sandwich-ab-results.md)。題材は R1〜R4 の匿名表記で、repo 名・test 本体・実名入りの詳細は private overlay にだけ置いた。

## 判定: REJECT（Opus 単独のままにする）

事前登録した REJECT 条件のうち「費用比が 0.85 を超える」に当たった。INCONCLUSIVE ではないので、反復 3〜4 の追加はしない。

| # | 基準（ADOPT の条件） | 結果 | 満たすか |
|---|---|---|---|
| 1 | 費用比 D / A' ≤ 0.70、bootstrap 95% 上限 ≤ 0.85 | **1.039**（95% [0.818, 1.286]） | 満たさない（REJECT 境界 0.85 も超える） |
| 2 | 成功率差 D − A' ≥ −5 pt、95% 下限 ≥ −15 pt | **+3.1 pt**（95% [0.0, +9.4]） | 満たす |
| 3 | leak 題材の隠しテスト失敗 run 数 D ≤ A' + 1 | A' = 3、D = 2 | 満たす |
| 4 | 盲検合計の差 D − A' ≥ −1.0（二重採点の平均） | **+3.52**（Opus のみ +2.83、gpt-6-astra のみ +4.20） | 満たす（reviewer 間で一致） |

要するに、受け入れテストがあれば **D は品質・成功率で Opus 単独と同等以上になったが、費用は Opus 単独とほぼ同じ（1.04 倍）で、事前登録した 30% 削減には届かなかった**。前回の B（2.34 倍）からは大きく縮んだが、「安くなる」という主張は支持されない。

- 本番の最初の起動は、実行環境のバックグラウンド実行の上限（2 時間）で切れる恐れがあったので約 1 分で止め、切り離したプロセスで起動し直した。止めた時点で記録済みの run は 0（作業中だった 2 run は最初から作り直した）。基準・harness・schedule は変えていない。
- 凍結時に記録した overlay の sha256（前回分 88 ファイル＋ `config-d.json`）は、本番の後も全ファイル一致した。

### 費用

- D の費用の内訳: Codex（gpt-6.1-sol）68.3%（run 平均 0.27 USD）、Opus の軽量レビュー 31.7%（run 平均 0.13 USD）。Codex は 32 run 中 31 run で 1 回の呼び出しで gate を通った（可視テストを Codex 自身が回して反復した）。
- **Codex だけでも A' の 0.71 倍**になる（参考の計算。判定には使わない）。軽量レビューを無料にしても基準 1 の 0.70 に届かない。D の費用を下げる余地は、レビューより Codex の入力（run 平均 58 万 token、うち cache 90%）にある。
- 題材ごとの費用比 D / A' は 0.38〜1.77。D が安かったのは 3 題材だけで、うち S04 は A' の 1 run が長考して高くついた（A' 平均 946 秒・0.97 USD）ことによる。13 題材では D の方が高い。単価の仮定（Codex の非 cache 入力をすべて cache write 単価で換算）を変えると 1.11 で、判定は変わらない。
- テストを可視にしても Opus 単独の費用は下がらなかった（前回 A 0.35 → A' 0.38 USD、時間 102 → 156 秒）。受け入れテストを回して直す分、むしろ少し増えた。
- 時間は D が A' の約 3 倍（Codex の実装が D の段階時間の 96%）。

| 題材 | A' | D |
|---|---|---|

| S16 | 0/2（ミュータント 2〜3/4） | 0/2（ミュータント 2/4） |

- 受け入れテストを可視にすると、両アームとも受け入れ合格率が 1.00 になった。前回の C の失敗（interface 未実装、受け入れ 5/11 など）は、テストの可視化と契約への interface 一覧の追加で消えた（前回 C 0.66 → 今回 D 0.94）。
- 残った失敗は、受け入れテストが確かめていないこと（S11 の隠しテスト 1 件、テスト追加の題材 S16 のミュータント）だけだった。
- テスト追加の題材のミュータント検出は A' 21/24、D 20/24（全部落とした run はどちらも 4/6）。

### リーク

- leak 題材の隠しテスト失敗は A' = 3（S16 × 2、S11 × 1）、D = 2（S16 × 2）。実装の題材で隠しテストを落としたのは A' の S11 の 1 run だけで、D は 0。

### 軽量レビュー（副次。判定に使わない）

- 32 run すべてで 1 回実施。判定は APPROVED 31、WARNING 1（must_fix 1 件、category requirements）、BLOCKED 0。must_fix 以外の指摘は should_fix 12 件・nit 47 件で、修正依頼にはつながらない。
- 修正依頼は 1 run（S02、「ギャップ明けのティックでの到達を有効にしている」という要件の指摘）。Codex の修正後に gate は通り、成功（採点）はレビュー前・最終とも成功で不変だった。この題材の隠しテスト（ギャップ行は invalid）はレビュー前から通っていたので、指摘が実際の欠陥だったかはこの採点では判定できない。
- レビュー前に隠しテストが落ちていた run は 2（どちらも S16 のテスト不足）で、レビューは 2 run とも APPROVED（リーク・テスト不足の指摘 0/2）。前回の B の工程内レビュー（0/2）と同じく、この題材集合では Opus のレビュー層が採点上の品質を変えた形跡は見えない。
- 軽量レビューの費用は run 平均 0.13 USD で、前回の B の計画＋レビュー（run 平均 0.58 USD）の約 2 割。

### 盲検の二重採点

- reviewer は Opus（effort high、ツール無し）と gpt-6-astra（effort high、read-only）。同じ pack の 2 組を両者が独立に採点した（候補 64 × 2 組 × 2 reviewer = 256 採点）。
- 一致度: 候補ごとの合計点で Pearson 0.680、Spearman 0.698、平均絶対差 2.03 点。leakage 軸で「リークあり（≤ 2）」の判断の一致率 0.891。基準 4 の可否は両 reviewer で一致（どちらも満たす）。
- **D − A' の +3.52 点の大半は tests 軸**（5 点満点で A' 2.05〜2.45、D 4.39〜4.75）。A' は、テスト追加以外の題材 26 run のうち 7 run で自分の test を足さなかった（D は 26/26、前回の A は 25/26 で足した）。盲検の diff には受け入れテストを入れないので、受け入れテストに頼って自分の test を書かなかった A' の候補は「テストなし」と採点される。他の 4 軸の差は −0.24〜+0.59 点で小さい。
- 両 reviewer とも、隠しテストが落ちた候補に leakage ≤ 2 を付けた割合は 0/2 だった（前回 0/8）。

## 逸脱と限界

1. **指示の非対称（前回から存在）**: D の契約の受け入れ条件には「変更した振る舞いを検証する test を追加または更新する」が入るが、A' のプロンプト（前回の A と同じ `solo-prompt.md`）には無い。可視テストのある A' はこの指示が無いために自前の test を省いた run があり、盲検の tests 軸で不利になった。基準 4 は D 有利の方向にずれた可能性があるが、判定は費用で決まっているので結論は変わらない。
2. **修正依頼の経路は本番で 1 回しか動いていない**（スモークでは 0 回、制御は selftest の stub で確認済み）。軽量レビューの有効性は、この題材集合の難度では測れていない。
3. **test と参照解の書き手は Opus**（前回と同じ準備用セッション）。今回は両アームが同じテストを見るので、テストの癖が一方に有利に働く偏りは前回より小さい。
4. **費用は API 料金表での換算値**で、サブスクリプションの実際の請求額ではない。Codex の単価は短い文脈の値で、長い文脈のリクエストがあれば D の費用は過小評価になる（D に有利な方向）。結論は変わらない。
5. **受け入れテストを作る費用は含めていない**（設計書 §1 の前提）。含めれば両アームに同額が乗り、費用比は 1 に近づくが、0.85 を下回ることはない。
6. **CLI の版**: Claude Code は前回（2.1.288）から 2.1.289 に上がっていた。本番中は変化なし。前回との比較は参考に留める。
7. gpt-6-astra の盲検採点は 32 回すべてでシェルコマンドを実行した（共有の規約ファイルの参照、空の作業ディレクトリでのファイル探索、手計算）。対応表・run ディレクトリ・overlay には触れていない（コマンドと出力を確認済み）。盲検は保たれたと判断する。

## 結論と示唆

- 「Codex が実装し、品質は事前テストで担保し、Claude は軽いレビュー」の構成は、**品質面では成立した**（テストを可視にすると Sol の弱点だった受け入れ失敗が消え、成功率・リーク・盲検で Opus 単独と同等以上）。
- しかし **費用面では Opus 単独と同等**で、事前登録の 30% 削減に届かない。比較相手の Opus 単独も、テストがあれば 1 回で通るので安いままだった。Codex 単体の費用（A' の 0.71 倍）が下限で、レビューを削っても基準 1 にはわずかに届かない。
- したがって、費用の削減を目的に D を標準にする根拠はない。D を選ぶ理由があるとすれば、Opus の利用枠の節約（Claude の費用は A' の 33%）や、テスト追加を確実に行わせる点であり、それはこの eval の判定基準の外にある。
