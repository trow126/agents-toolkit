# A/B 結果: サンドイッチ手法（Opus 計画 → Sol 実装 → Opus レビュー）と Opus 単独

実行: 2026-10-03〜04。設計と判定基準: [sandwich-ab-design.md](sandwich-ab-design.md)（凍結コミット `1a15c1e`、本番の run を 1 つも始める前に凍結）。題材は R1〜R4 の匿名表記で、repo 名・test 本体・実名入りの詳細は private overlay にだけ置いた。

## 判定: REJECT（Opus 単独のままにする）

事前登録した REJECT 条件のうち「費用比が 0.85 を超える」に当たった。INCONCLUSIVE ではないので、反復 3〜4 の追加はしない。

| # | 基準（ADOPT の条件） | 結果 | 満たすか |
|---|---|---|---|
| 1 | 費用比 B / A ≤ 0.70、bootstrap 95% 上限 ≤ 0.85 | **2.341**（95% [2.134, 2.602]） | 満たさない（REJECT 境界 0.85 も超える） |
| 2 | 成功率差 B − A ≥ −5 pt、95% 下限 ≥ −15 pt | **+9.4 pt**（95% [0.0, +25.0]） | 満たす |
| 3 | leak 題材の隠しテスト失敗 run 数 B ≤ A + 1 | A = 2、B = 2 | 満たす |
| 4 | 盲検合計の差 B − A ≥ −1.0（二重採点の平均） | **+0.97**（Opus のみ +0.86、gpt-6-astra のみ +1.08） | 満たす（reviewer 間で一致） |

要するに、サンドイッチ手法は **品質と成功率では Opus 単独と同等以上だが、費用は 2.3 倍** だった。主張された「30〜50% の削減」とは逆向きである。

## 実行の記録

- 96 run（16 題材 × 3 アーム × 2 反復、seed 20261003、並列 2）。全 run を記録し、除外は 0（harness エラー 0、汚染 0、rate limit 0）。全 run で Claude Code 2.1.288・codex-cli 0.159.3（途中の版の変化なし）。
- 本番の run が 6 時間 0 分、盲検の二重採点（64 回）が 52 分。準備（題材 16 件の test・参照解・罠版・ミュータントの作成と機械検証、harness の修正、玩具 repo でのスモーク）から凍結までは約 1 時間。
- 凍結時に記録した overlay の sha256（設計書 §11.3）は、本番の後も全ファイル一致した。

### 費用（懸念 3 への答え: ハンドオフのオーバーヘッドで節約分は消える。そもそも節約が無い）

- B の費用の内訳: Opus の計画 47.3%、Opus のレビュー 23.0%、Codex（gpt-6.1-sol）29.7%。**計画 1 回の平均費用（0.39 USD）が、A が実装を最後まで終える費用（0.35 USD）を上回る。**
- Codex を無料と仮定しても、B の Claude 部分だけで A の 1.64 倍になる。題材ごとの費用比 B / A は 1.72〜3.59 で、16 題材すべてで B の方が高い。単価の仮定（Codex の非 cache 入力をすべて cache write 単価で換算）を変えても 2.41 で、判定は変わらない。
- Claude の `total_cost_usd` は、Anthropic 公式の Opus 5.5 単価（input 4、cache write 5 分 5 / 1 時間 8、cache hit 0.20、output 20 USD/MTok）で usage から再計算した値と一致した。
- 時間も B が A の約 6 倍（Codex の実装が B の段階時間の 79%）。

### リーク（懸念 2 への答え: 今回の題材では Sol 実装 + Opus レビューでリークは増えなかった）

- leak 題材の隠しテスト失敗は A = 2、B = 2、C = 8。A・B の 2 件はどちらも S16（テスト追加の題材で、書いたテストがミュータントを全部は落とせなかった）。実装の題材で隠しテスト（未来の摂動・接頭辞不変・感度）を落とした run は、A・B とも 0。
- C は 8 件（S06・S14・S16・S11 の各 2）。B と C の隠しテスト合格率の差は +21.4 pt で、計画（時点整合の制約を明記する §5）が Sol の実装のリークを減らしている可能性がある。ただし C には下の逸脱がある。
- B の工程内レビューは 32 run すべてで 1 回目に APPROVED（must_fix 0、再委任 0）。隠しテストが落ちた round は 2 つ（どちらも S16 のテスト不足）で、レビューはどちらもリークを指摘しなかった（0/2）。工程内レビューが品質に寄与した形跡は、この題材集合では見えない。

### 盲検の二重採点

- reviewer は Opus（effort high、ツール無し）と gpt-6-astra（effort high、read-only）。同じ pack の 2 組を両者が独立に採点した（候補 96 × 2 組 × 2 reviewer = 384 採点）。
- 一致度: 候補ごとの合計点で Pearson 0.645、Spearman 0.443、平均絶対差 1.92 点。leakage 軸で「リークあり（≤ 2）」の判断の一致率 0.948。基準 4 の可否は両 reviewer で一致（どちらも満たす）。
- Opus reviewer は A（自系統）を最も低く付けた（A 21.91 / B 22.77 / C 22.70）。gpt-6-astra は C を最も高く付けた（A 20.75 / B 21.83 / C 23.64）。今回の採点では、Opus の自系統びいきは見えなかった。
- 両 reviewer とも、隠しテストが落ちた候補に leakage ≤ 2 を付けた割合は 0/8 だった。diff を読むだけの盲検 reviewer は、この eval で検出したリーク・テスト不足を見つけられていない。盲検の点数は C の失敗（interface 未実装・隠しテスト失敗）をほとんど反映しておらず、品質の指標としての弁別力は弱い。

### 参照の判断（arm C）

C の成功率差 C − A は −18.8 pt（95% 下限 −43.8 pt）で基準 2 を満たさない。費用は B の 30%、A の 70%。設計書 §7 の条件（C が基準 2〜4 を満たし B より安い）は満たさないので、「Opus の計画とレビューの層は費用に見合わない」とは記録しない。ただし、Opus 単独（A）より高いので、層の価値は「C を A 並みにすること」には及ぶが「A より安く同等にすること」には届いていない。

## 逸脱と限界

1. **arm C の契約に interface 一覧が入っていなかった（harness の不具合、本番後に発見）**。`contract_for` は本文と受け入れ条件だけを契約に入れ、題材の `interface` を入れていなかった。設計書 §2 の「全アームに同じ interface を渡す」からの逸脱である。A は solo-prompt で、B は Opus の計画（§3 interface）経由で受け取っている。新しい関数名が interface にしか書かれていない S11・S12 で、C は 4 run とも受け入れテストの collection で落ちた。凍結後なので再実行はせず、感度分析だけ示す: S11・S12 を除くと C の成功率は 0.75、C − A は −7.1 pt（依然として基準 2 を満たさない）、隠しテスト失敗は C = 6。主比較（A と B）には影響しない。
2. **実題材の pilot を省略した**（owner の判断）。代わりの玩具 repo のスモークで harness の不具合を 4 件直してから凍結した（設計書 §11.2）。本番では基盤エラーは 0 件だった。
3. **test と参照解の書き手は Opus**（アームと別のセッション。owner のレビューなし）。結果は B が A 以上だったので、A に有利な偏りがあったとしても結論（費用で REJECT）は変わらない。
4. **環境の差による必須 check の修正**: R2・R4 で、mirror に入らない gitignore 済みデータを読む既存 test（R2 2 件、R4 1 件）を全アームで `--deselect` した。
5. **gpt-6-astra の盲検採点は 32 回すべてでシェルコマンドを実行した**（規約ファイルの参照、空の作業ディレクトリでのファイル探索）。1 回だけ eval のルートディレクトリの一覧を取り、対応表のファイル名を見たが、中身は読んでいない（コマンドと出力を確認済み）。盲検は保たれたと判断する。
6. **B の工程内レビューが一度も must_fix を出さなかった**ので、再委任の経路（WARNING → 再委任）は本番で一度も動いていない。レビュー層の効果は、この題材集合の難度では測れていない。
7. **Codex の単価は短い文脈（1 リクエストの入力 ≤ 272K）の値**。Codex の usage はリクエスト単位でないので、長い文脈があれば Codex の費用は過小評価になる（B に有利な方向）。結論は変わらない。
8. **費用は API 料金表での換算値**で、サブスクリプションの実際の請求額ではない。
