# --apply

Implements a finished run. Invoking `/skill-tuneup --apply <run-dir>` is the request to edit the repository files listed below and run the checks; it is not a request to commit, push, or open a PR.

1. Run `~/.claude/bin/skill-tuneup plan <run_dir>`. It fails unless `finish` passed for the run, HEAD is the inventoried commit or a descendant of it, and no file of the run's skills has changed since that commit (committed or uncommitted). If `finish` has not passed, complete the run first; if skill files have changed, rerun the default flow with `--only` for those skills; if HEAD is neither the inventoried commit nor a descendant, report the mismatch and stop. It prints, per skill, the hygiene findings grouped by effect and the candidates whose experiment passed (`PASS`), each with its audit verdict (`KNOWN`, `PARTIAL`, or `NOT_FOUND`).
2. Load `implementation-quality` and follow its rules for each change. Implement only what `plan` printed. A printed candidate whose audit verdict is `KNOWN` is implemented as the known method with its source cited; candidates from an experiment with a `FAIL` or `INCONCLUSIVE` verdict are not implemented. Hygiene findings that remove or correct text are implemented. A finding that adds an instruction is implemented only when its evidence names the line of `<run_dir>/research.md` that mandates it; otherwise report it as needing an experiment and leave it out, since compliance falls as instructions accumulate and a static review does not predict outcomes. For a finding printed as `unclassified` (no effect recorded), apply whichever of these two hygiene rules matches what its fix does.
3. Keep each skill's change inside its own files plus the contracts the toolkit checks: the skill-pair drift fixture, `docs/contracts/skill-authority.tsv` when a mode changes, inventory rows for new files, and the `metrics:after` block when skill sizes change. Update the skill's own evidence file when a change rests on new evidence.
4. Run the static suite from the toolkit repository root. Execute the tests as files, not as arguments to `bash`: `for t in tests/test-*.sh; do "$t" || echo "FAIL $t"; done`, then `scripts/validate-layout.sh`, `scripts/lint-distributed-markdown.sh`, and `shared/bin/sync-shared-rules.sh --check`.
5. Report per skill what changed (files) and what was skipped and why, and report the check results including every failing check with its output (`--apply` is not done while any check fails). Leave the changes uncommitted; the user commits with `git-operations` or `gh-finish`. Do not invoke a skill changed by this `--apply` in the same conversation, and tell the user in the report that the changed skills take effect in a new conversation.
