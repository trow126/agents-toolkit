# break-consensus — 合意破壊型の革新探索

通常の brainstorming ではない。目的は「良さそうな案を早く出す」ことではなく、**LLM と業界が最初に到達する高確率解を可視化して封鎖し、そこから構造的に離れた候補だけを生成・審査・実験化する**こと。

根拠と出典は [references/evidence.md](references/evidence.md) を参照（LLM 発想の均質化・fixation・類推距離・novelty 監査の実証研究）。

## 起動条件（厳守）

- **手動起動のみ**（frontmatter で自動起動を無効化済み）。ユーザーの明示起動なしにこのプロセスを開始しない
- 以下では**使わない**: 通常のバグ修正、security patch、production incident、migration 実行、単純な実装、明確な仕様に従う作業、最小変更を要求された作業、fact lookup、定型 refactoring
- 生成した候補を、ユーザーの採用判断なしに production コードへ実装しない

## 引数

- `--domain <領域>`: 対象領域を明示（例: `--domain データパイプライン`）
- `--depth light|standard|deep`（既定: standard）
  - **light**: Stage 1-3 + 6-7。異分野移植を省略、novelty 監査は既知範囲の自己申告 + 明示的な未検証宣言
  - **standard**: 全 Stage。異分野 2-3 分野、novelty 監査は Explore/Web 調査 1 回
  - **deep**: 全 Stage。異分野 4+ 分野、候補ごとに独立 novelty 監査、deep-reasoner による審査

## エージェントの再利用（新規常設 agent を作らない）

- 大量調査（既存事例・競合実装・文献）: **built-in Explore**（read-only）+ WebSearch
- 候補の構造審査・実験設計の妥当性判断: **deep-reasoner**（判断のみ）
- 採用候補のスコープ・リスク批評: **plan-reviewer**（通常経路への引き渡し前）

## 探索プロセス

### Stage 1: Problem Frame（問題の枠組み）

明確化する: 解決対象 / 本当に達成したい結果 / 現在の制約 / 成功指標 / 変更可能なもの / 変更不能と**仮定している**もの / 問題設定自体が誤っている可能性。

不足情報があっても長い質問票を返さない。合理的仮定を明示して開始し、結果を大きく左右する不足だけ質問する。

### Stage 2: Consensus Map（合意領域の可視化）

対象問題の典型解・多数派解・安全解・既知解を列挙する: 業界標準 / LLM が最初に出しやすい案（自分がまず思いつく案を正直に書き出す）/ 競合製品の一般的方式 / 専門家が無難に勧める方式 / 過去に成功した代表方式 / 現行実装がすでに採用している方式。

各案を concept cluster（解決原理ごとの束）へまとめ、**baseline として固定する**。以降の候補が「これらの言い換えか」を判定する基準になる。合意領域は否定しない — 封鎖するだけ（最終的に合意解が最良なら、それは Stage 7 で実験により示されるべき結論）。

### Stage 3: Assumption Destruction（前提の破壊）

Stage 1-2 に潜む暗黙の前提を列挙し、各前提へ次の操作を試す: 削除する / 反転する / ゼロにする / 100 倍にする / 責任主体を変える / 時間方向を逆転する / 成功と失敗の定義を入れ替える / 問題を解かない方法を考える / 副作用を主目的に変える。

各操作について**探索空間がどう変わったか**を 1 行で説明する（変わらない操作は捨てる）。

### Stage 4: Remote Mechanism Transfer（異分野機構の移植）

対象領域から**遠い**分野を depth に応じて複数選ぶ。候補例: 免疫系 / 進化生物学 / 生態系 / 予測市場 / 金融市場 / 航空管制 / 法廷手続 / 製造品質管理 / 科学的方法 / エラー訂正符号 / 分散システム / 統計的実験計画 / 軍事的 red teaming / オープンソースの競争的協調。

表面的な role-play・比喩で終わらせない。分野ごとに抽出する:

1. その分野が解いている抽象的問題
2. 中核メカニズム
3. 成立条件
4. 失敗モード
5. 対象問題との構造的対応関係
6. 移植後の最小検証方法

構造的対応（5）が書けない分野は移植せず捨てる。類推は「遠すぎても近すぎても効かない」— 対応関係の実在が採用条件（evidence.md 参照）。

### Stage 5: Forced Heterogeneity(生成原理の強制多様化)

候補数だけを増やさない。**候補の生成原理を重複させない**:

- 各候補に生成原理タグを付ける（例: `前提反転:時間逆転` / `移植:免疫系-負の選択` / `合意解の極端化` / `副作用の主目的化`）
- 同一原理タグの候補は最良 1 件に統合する
- 最終候補セットは原理タグがすべて異なる 3-7 件とし、各候補について「Stage 2 のどの cluster とも原理が異なる」ことを 1 行で示す
- 判定に迷う候補は Stage 2 cluster の言い換えとみなして落とす（グレーは baseline 側に倒す）

### Stage 6: Novelty Audit（独立調査による既視感の排除）

候補ごとに、**生成した文脈から独立に**類似の既存事例を探す:

- Explore / WebSearch で機能・機構ベースの検索を行う（候補の自称名ではなく、動作原理・入出力構造で検索する）
- 見つかった最近傍事例を candidate ごとに記録する: 事例名 / 出典 / 一致点 / 相違点
- 判定: **既知**（実質同一の先行あり → 落とすか、先行の採用提案に切替）/ **差分あり**（先行はあるが中核機構が異なる → 差分を明記して残す）/ **新規らしい**（見つからず → 「調査範囲で未発見」と明記。新規と断定しない）
- ungrounded な「これは新しい」という自己判断を採用しない（検索に基づかない novelty 判定は信頼できない — evidence.md）

### Stage 7: Falsifiable Experiment（反証可能な最小実験への変換）

生存候補を、それぞれ**最小コストの実験**に変換する:

- **価値仮説**: この候補が正しければ何が観測されるか
- **反証条件**: 何が観測されたら捨てるか（事前に固定。動かさない）
- **最小実験**: 反証条件を最速・最安で踏みにいく手順（目安: 1 セッション内で実行可能な規模まで削る）
- **測定**: baseline（Stage 2 の合意解または現行実装）との比較方法

アイデアの紙上評価と実装後の実力は乖離する（evidence.md）。実験なしの「有望」を成果物にしない。

### 出力と引き渡し

最終出力（`claudedocs/brainstorm/break-consensus-[YYYYMMDD-HHMM].md` に保存）:

```
# break-consensus: <問題>

## Problem Frame（仮定を含む）
## Consensus Map（cluster 一覧 = 封鎖済み baseline）
## 生存候補（3-7 件）
   各: 生成原理タグ / 中核機構 / novelty 判定と最近傍事例 / 価値仮説 / 反証条件 / 最小実験 / 期待される優位と主なリスク
## 落とした候補（原理重複・既知・構造対応なし）と落とした理由
## 推奨する次の一手（実験の実行順と判断ポイント)
```

- ユーザーが実験実行を選んだ候補だけを**通常の実装経路**（最小コスト owner + 必要なら plan-review）へ渡す
- production 実装は標準的・単純・可逆・検証可能にする。新規性を置く場所は価値仮説または中核メカニズムに限定し、周辺実装には成熟した既存技術とプロジェクト標準を使う
- この skill の探索モードを通常のコーディング作業へ持ち越さない
